# el-town 100町内会運用に向けた実施計画

- 作成日: 2026-08-20（JST）
- 対象規模: 最大100町内会・自治会、50,000世帯、LINE連携利用者75,000人
- 想定ピーク: 2,500同時利用、API 100〜200リクエスト/秒
- 基準構成: Next.js、Netlify、Supabase、Stripe、LINE
- 抜粋元: `docs/reports/operations_architecture_scalability_codex_2026-08-19.md`

## 1. 結論

100町内会までは、現行の `Netlify + Next.js + Supabase + Stripe + LINE` を単一セルで維持する。Kubernetes、町内会ごとのSupabase Project、マイクロサービス群への先行移行は行わない。

ただし、現在の構成をそのまま団体数だけ増やしてはいけない。100団体運用開始前に、認証、テナント分離、バックアップ、非同期処理、監視、監査、負荷試験を完成させる必要がある。

## 2. 100町内会時点の目標構成

| 項目 | 目標構成 |
|---|---|
| Web | Netlify本番サイト1、ステージングサイト1 |
| API | Next.js Route Handler、Netlify Functions |
| DB/Auth | Supabase有償本番Project 1、ステージングProject 1 |
| Storage | Supabase Storage＋外部増分バックアップ |
| 非同期処理 | ジョブテーブル＋ワーカー、必要に応じBackground Functions |
| Stripe | Platform 1、1団体1 Connect account |
| LINE | 配信キュー、500人単位のmulticast、retry key保存 |
| 運用 | system管理画面、監視・監査ログ、承認付きCodex運用支援 |

運用目標は、月間可用性99.9%、API P95 1秒以内、主要画面P75 2.5秒以内、重要ジョブ成功率99.9%とする。

## 3. これから実施すること

### P0: 最優先で解消する安全上の問題

#### 1. 会員認証をサーバー検証方式へ変更

- LIFF ID tokenをサーバー側で検証する。
- 予測可能なSupabase認証情報へ依存する方式を廃止する。
- 不正、期限切れ、別チャネル、別団体のtokenを拒否するテストを追加する。

完了条件:

- 会員認証がクライアント側の入力値だけでは成立しない。
- 正常系と拒否系をCIまたは自動テストで再現できる。

#### 2. system管理者の既定資格情報を廃止

- `SYSTEM_LOGIN_ID`、`SYSTEM_LOGIN_PASSWORD`、`SYSTEM_SESSION_SECRET` の既定値を削除する。
- 本番で未設定の場合は、起動またはログインを拒否する。
- system管理、GitHub、Supabase、Netlify、Stripe、LINEでMFAを必須化する。

完了条件:

- リポジトリ内に有効な既定資格情報が存在しない。
- 本番秘密情報が欠けた状態で安全側に停止する。

#### 3. 全テーブルとStorageのRLS監査

- 全業務テーブルに変更不能な `tenant_id` を持たせる方針を確定する。
- SELECT、INSERT、UPDATE、DELETEのRLSを役割別に検査する。
- Storage pathへtenant prefixを強制し、他団体のファイルを参照できないことを確認する。
- `service_role` がブラウザへ渡らないことを自動検査する。

完了条件:

- 他テナント参照・更新を防ぐ回帰テストが合格する。
- 全テーブルと全Storage bucketの監査結果が文書化される。

### P1: 障害時に復旧できる基盤を作る

#### 4. 本番・ステージング・開発を完全分離

- Netlify、Supabase、Stripe、LINEの環境と資格情報を分ける。
- ステージングへ本番個人情報を複製しない。
- Node.jsバージョンをローカル、CI、Netlifyで統一する。
- 本番デプロイは現行の承認付き手順を継続する。

#### 5. DBとStorageのバックアップを実装

- Supabase PITRを7日以上有効化する。
- DB論理dumpを毎日、Supabase外へ暗号化保存する。
- Storageを1時間ごとに外部へ増分コピーする。
- 月1回、別環境へのDB・Storage復元試験を行う。
- 四半期ごとにStripe、LINE、DNSを含む全体復旧訓練を行う。

目標:

- DB RPO 5分以内、RTO 2時間以内
- Storage RPO 1時間以内
- アプリRTO 30分以内

完了条件:

- バックアップの存在確認だけでなく、別環境へ復元して件数とファイルを照合できる。

### P1: 大量処理を非同期化する

#### 6. 共通ジョブ基盤を導入

ジョブに最低限、次の項目を持たせる。

```text
job_id / tenant_id / cell_id / job_type / idempotency_key
status / attempt_count / scheduled_at / started_at / finished_at
payload_reference / result_reference / last_error_code
```

状態は `queued`、`running`、`succeeded`、`retry_wait`、`failed`、`cancelled` とし、ワーカー停止後に再開できるリース期限を持たせる。

#### 7. LINE一括配信をジョブ化

- 対象者を500人単位に分割する。
- 実送信前にメッセージ検証APIを通す。
- `X-Line-Retry-Key` を保存し、再試行時の重複送信を防ぐ。
- 成功、失敗、ブロック、429、対象数をtenant単位で記録する。
- 緊急配信と通常配信で優先度を分ける。

#### 8. Stripe Webhookを受付と業務処理に分離

- 署名検証後、イベントを保存して速やかに応答する。
- `stripe_event_id` を一意保存する。
- Connect account IDと `tenant_id` を一意に関連付ける。
- 重複、再送、順序逆転、集中受信をテストする。
- PaymentIntent、Invoice、金額、通貨、tenantを照合する。

#### 9. 月次請求を冪等ジョブ化

- `tenant_id + fiscal_period + billing_type` を業務キーにする。
- 一括処理は対象行ごとに成功・失敗を記録する。
- 一時障害だけを指数バックオフで再試行する。
- 請求、返金、口座変更は人間の承認を必須とする。

完了条件:

- LINE、Stripe、月次請求をブラウザの同期リクエスト完了に依存しない。
- 同じ入力を再実行しても重複送信・重複請求・重複計上が起きない。

### P1: 監視・監査・容量管理を整備する

#### 10. 監査ログを導入

- 操作種別、操作者、tenant、対象ID、承認ID、実行結果を記録する。
- 本番デプロイ、権限変更、一括処理、Stripe操作、LINE配信を追跡可能にする。
- 本人確認書類、カード番号、口座画像、秘密情報は記録しない。

#### 11. 監視と初期アラートを設定

監視対象:

- 公開URL、API、LIFFの死活
- HTTP 4xx/5xx、API P95/P99
- DB CPU、メモリ、接続数、IO、遅いSQL
- Storage容量、転送量、失敗率
- ジョブ件数、最古ジョブ、retry、failed
- LINE成功率、429、月間上限
- Stripe Webhook失敗、未処理、重複
- 認証失敗、RLS拒否、管理者操作
- バックアップ、復元試験、デプロイID

初期アラート:

- APIエラー率が5分間で2%超
- API P95が2秒超
- DB接続数またはCPUが上限の70%超
- 最古の重要ジョブが5分以上
- Stripe Webhook失敗が1件以上
- LINE 429または月間上限80%到達
- バックアップまたはRLS回帰テスト失敗

#### 12. 画像・添付ファイル管理を整備

- 形式、寸法、容量をアップロード時に検査する。
- Web表示用画像とサムネイルを生成する。
- ハッシュで重複保存を抑止する。
- `tenant_id/yyyy/mm/` 等のStorage prefixを使用する。
- 保持期間、削除、退会・解約時の保管方針を定義する。

### P2: 100町内会の負荷試験と受入判定を行う

匿名化したステージングで次を実施する。

1. 2,500同時利用者
2. API 100〜200リクエスト/秒
3. 50,000人分のLINE配信ジョブ生成
4. 500人単位への分割とretry keyによる再送
5. Stripe Webhookの重複、順序逆転、集中受信
6. 画像アップロードとサムネイル生成
7. 会費年度更新と帳票生成
8. 1テナントの大量アクセスが他テナントへ与える影響
9. DB接続枯渇、ワーカー停止、外部API 429
10. 前バージョンへのロールバック

LINE本番環境への大量送信は行わず、送信部分をモックまたは検証APIへ置き換える。

## 4. 推奨実行順序

| 順序 | 作業 | 主な成果物 |
|---:|---|---|
| 1 | 現行認証、RLS、同期処理、環境構成の棚卸し | 現状一覧、リスク台帳、対象コード一覧 |
| 2 | 会員認証とsystem管理者認証のP0修正 | 認証設計、自動テスト、移行手順 |
| 3 | tenant IDとRLS・Storage Policyの統一 | migration、policy、回帰テスト |
| 4 | 本番・ステージング分離 | 環境台帳、秘密情報一覧、CI設定 |
| 5 | PITR、DB dump、Storage外部バックアップ | バックアップジョブ、復元手順、復元記録 |
| 6 | 共通ジョブテーブルとワーカー | job schema、worker、再試行・監視 |
| 7 | LINE、Stripe、月次請求のジョブ移行 | 冪等処理、結果台帳、運用手順 |
| 8 | 監査ログ、監視、アラート | ダッシュボード、通知先、障害手順 |
| 9 | 画像・容量管理 | 変換処理、保持方針、容量レポート |
| 10 | 負荷試験、復旧試験、受入判定 | 試験結果、未解決課題、運用開始承認 |

P0の認証・RLSが完了する前に、団体数を増やす施策を優先しない。非同期化は共通ジョブ基盤を先に作り、LINE、Stripe、請求の順で段階移行する。

## 5. 100町内会運用の受入チェックリスト

- [ ] 会員認証がLIFF ID tokenのサーバー検証方式になっている
- [ ] system管理者の既定資格情報が存在しない
- [ ] 他テナント参照・更新を防ぐRLSテストに合格している
- [ ] 全Storage bucketのtenant分離を検証している
- [ ] 本番とステージングが完全に分離している
- [ ] DBとStorageを別環境へ復元できる
- [ ] LINE配信の500人分割、retry key、結果記録を確認している
- [ ] Stripe Webhookの署名、重複、順序逆転、再試行を確認している
- [ ] 月次請求を再実行しても重複請求されない
- [ ] 監査ログで重要操作を追跡できる
- [ ] 監視、アラート、担当者、重大障害連絡先が定義されている
- [ ] 50,000世帯を前提とした負荷試験に合格している
- [ ] ロールバックと月次復元試験を実施している
- [ ] 本番デプロイが承認付きで監査可能である
- [ ] `tenant_id` と将来用の `cell_id` を持っている

## 6. 今すぐ着手する最初の5作業

1. 会員認証とsystem管理者認証の現行コード、環境変数、入口を棚卸しする。
2. Supabaseの全テーブル、RLS、Storage bucket、policyを一覧化する。
3. LINE配信、Stripe Webhook、月次請求の同期処理とデータ更新箇所を一覧化する。
4. 本番・ステージングのNetlify、Supabase、Stripe、LINE対応表を作る。
5. P0修正の担当者、期限、レビュー担当、受入テストを決める。

この5作業の結果を基に、P0修正を個別チケットへ分割し、認証とテナント分離から実装を開始する。

## 7. 100町内会段階では行わないこと

- 100団体分のSupabase Projectを個別作成しない。
- 10,000団体向けのマイクロサービスを先行して大量作成しない。
- 表示名をtenant IDとして使用しない。
- LINE配信、Stripe処理、月次請求を同期リクエストだけで完了させない。
- 本番データを開発・ステージングへ複製しない。
- Codexや運用担当へ無制限の本番権限を与えない。
- バックアップの取得だけで完了とせず、必ず復元試験を行う。
